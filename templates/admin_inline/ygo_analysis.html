%%STYLE%%

Analyse display / case (YGO)

%%ACTIONS%%

Outil interne : estime la valeur attendue (EV) d’une unité d’achat (display ou case) à partir de cartes, prix et hypothèses de liquidité. Connexion session admin (cookies) ou en-tête X-Admin-Key selon la config. Les champs envoyés au calculateur sont ceux du formulaire ci-dessous (JSON DisplayInput). La dérivation des pondérations accepte derive_mode (slot_mass ou case_expected_copies).

Légende — à quoi correspondent les infos
Chargement API
Interroge YGOPRODECK : liste du set (passcodes + signaux), puis prix Cardmarket par carte. Ne modifie pas l’analyse tant que vous n’avez pas cliqué sur Analyze.
Nom du set (API)
Doit correspondre au nom de set côté YGOPRODECK / Cardmarket (ex. « Legacy of Destruction »). Paramètre name de GET /admin/ygo/set.
Prix min. filtre
Seuil en EUR sur le prix Cardmarket global renvoyé dans card_prices pour garder une carte candidate. Défaut 2,00.
Coût (display_cost)
Montant payé pour l’unité analysée (un display ou une case) : sert à comparer l’EV et le niveau de risque. Alignez ce montant avec le mode de dérivation (masse relative vs espérances par case).
Nouveau set
Coche si les prix sont encore instables : ajoute un avertissement dans les résultats (is_new_set).
Lignes « version »
Chaque ligne avec champs est une entrée CardData : une impression / prix Cardmarket. Le groupe grisé = une même carte (même passcode).
EV de base / pessimiste / optimiste
Scénarios de décote sur le « prix réalisable » (×1, ×0,75, ×1,15) avant somme pondérée par la probabilité de tirage.
Prix d’achat prudent / équitable
Indicateurs dérivés de l’EV de base (70 % et 85 %) pour borner un prix d’achat raisonnable de l’unité (display ou case).
Top cartes
Cartes qui contribuent le plus à l’EV (après probabilité et décotes liquidité / réimpression).

Chargement YGOPRODECK

Renseignez le nom du set tel qu’attendu par l’API, puis Charger les cartes. Le serveur enchaîne une requête « liste du set » puis une requête prix par carte (d’où le délai). Les lignes du tableau sont ensuite éditables avant Analyze.

Cartes

Chaque ligne avec champs devient un objet CardData dans le JSON (nom, rareté moteur, probabilité, prix, stock, vélocité, tendance, risque réimpression). Après chargement API, les lignes grisées regroupent les versions d’une même carte ; la colonne « Nom » sur une sous-ligne affiche le libellé rareté Cardmarket si disponible. Les listes déroulantes utilisent les noms d’enum Rust attendus par le serveur.

Indiquez le coût du display pour une unité (un display scellé ou une case, selon votre analyse) ; alignez les comptages ci-dessous sur la même unité.

Composition produit — dériver les pondérations (pull_probability)
Mode derive_mode

Une ligne par rareté : libellé puis tabulation ou « | » puis le nombre (masse relative). Les libellés matchent la colonne « Nom / version » (Cardmarket) ou la rareté moteur. Répartition uniforme entre les lignes d’une même clé ; puis normalisation pour somme = 1 − bulk_mass.

Comptages : hits par case par rareté (Qk). Distincts : nombre de cartes distinctes du set par rareté (Dk). Chaque ligne reçoit Q_k / D_k (approximation uniforme avec remise). bulk_mass est ignoré (restez à 0).
