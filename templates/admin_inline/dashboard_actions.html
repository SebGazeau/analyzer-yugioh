Actions

Analyse display (YGO)

Estimation EV / liquidité / risques sur un display (données saisies, sans base).

Ouvrir l’outil

Catalogue YGOProDeck

Interroge l’API publique YGOProDeck, met à jour les tables cards et card_sets, peut écrire le fichier cards.json selon la config, puis recharge le cache utilisé par la recherche. À lancer sur une base vide ou après de nouvelles sorties de cartes.

Enrichissement YGOrganization (YGResources)

Enrichit la base avec des données YGOrg (effets EN, JSON cartes, etc.). Ordre conseillé la première fois : sync index → init révision → backfill (répéter si besoin) → manifest. Ensuite, sync Q&A de temps en temps pour le module « cartes associées ».

  • Sync index EN : télécharge l’index des noms anglais (volumineux, à faire rarement).
  • Init révision : enregistre la révision YGOrg de référence pour les manifests suivants.
  • Backfill : associe les passcodes de cards aux IDs YGOrg via l’index.
  • Manifest : télécharge le JSON brut des cartes (couche card_raw).
  • Sync Q&A : importe des Q&A récents (liens entre cartes pour l’UI associations).

Complément archétype (YGOrg)

Cible : cartes sans archétype YGOProDeck mais avec couche card_raw. Liste CSV (preview_card_metadata_fill) sans analyse JSON. Phases 2–3 (apply_card_metadata_fill) : dérive depuis le JSON (monstre : \"…\" monster ; sort/piège : add 1 \"…\" card sur la 1re ligne ; ou champ futur cardData.en.archetype). Avec write=1 : cards.archetype + archetype_source (NULL-only), recharge du cache. Sinon simulation.

Images illustrées

Parcourt les URLs d’images référencées en base, télécharge et produit les variantes WebP. Les images déjà importées sont en principe ignorées (pas de re-traitement inutile).

Fichiers de stockage

Pour chaque enregistrement images, retélécharge depuis l’URL source et écrit les fichiers aux chemins déjà en base (ex. dossier vide après déploiement ou changement de stockage). Forcer réécrit même si le fichier existe déjà.
